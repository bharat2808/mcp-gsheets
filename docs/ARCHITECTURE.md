# GSheets local plugin architecture

The plugin is a local stdio MCP server. Google OAuth uses the installed-app loopback flow with PKCE and no client secret. OAuth tokens and the 256-bit local data key are stored in the operating-system credential vault through `@napi-rs/keyring`.

Only Google Sheets beneath explicitly selected My Drive folders enter the catalog. Files carrying a shared-drive ID are discarded. At startup and every five minutes while the server is running, the server checks Drive file versions. Sheet values are downloaded and compared only when a version changed, then encrypted SQLite row snapshots and native table metadata are transactionally replaced. Each row keeps formatted values for search/preview and raw values for type-safe conflict checks. Search uses HMAC blind tokens over both forms; cell payloads, headers, tables, selected folder IDs, change summaries, and write audits are AES-256-GCM encrypted at rest.

Drive exposes a file revision, not cell-level deltas. Semantic added, modified, deleted, and structural groups are computed by comparing consecutive local snapshots. An identifier-like unique column is preferred; otherwise physical row number is used.

Writes use expiring proposals. Only append and row update are supported. The MCP App is the only caller allowed to approve, edit, or cancel. The proposal ID is visible to the model, but the approval nonce is delivered only through MCP result metadata to the app. Approval checks that nonce, the Drive revision, and current raw target values immediately before writing. Append proposals reject duplicate values in a detected identifier column. Updates use `values:batchUpdate` with one exact cell range per proposed column, so untouched cells and formulas are never rewritten. Google Sheets does not provide an atomic value-update revision precondition, so a narrow race remains between preflight and the API write; the plugin verifies the written values, stores an encrypted audit record, and refreshes immediately after a successful write.
